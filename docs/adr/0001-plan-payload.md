# ADR-0001: しおり（plan）を構造化データとしてチャットレスポンスに同梱する

## ステータス
Proposed（2026-10-11）

- 「plan の形」（決定 2〜4）は 2026-10-11 の壁打ちで合意済み
- 「チャットレスポンスに同梱する」（決定 1）と「フロントでの保存先」（未決定事項）は、次の会話で確認してから Accepted にする

## 文脈

- v1.0.0 の完成の定義は「AI が組んだルートが、左右分割画面の右側に番号付きピンで表示される」こと。ピンを立てるには、訪問順と座標がフロントに必要
- 現在フロントに届くのは Gemini の文章だけ（`main.py:137` の `{"choices": [{"message": {"content": text}}]}`）。座標・訪問順・時刻はバックエンドのセッション（`Guidebook`）の中にしかない
- 文章から座標や時刻を読み取る方法は、AI の言い回しに左右されて壊れやすい
- フロントは会話IDを送っていない。バックエンドは「第一声の SHA-256 ハッシュ」でセッションを特定している（`main.py:95-97`）
- `Guidebook` は2つの役割を兼ねている
  - **AI の作業メモ**：`missing_fields()` で「足りない欄」を毎回プロンプトに埋め込む
  - **旅行者に渡すしおり**：今回フロントに送ろうとしているもの
- 作業メモとして育ってきたため、しおりとして見ると形が不自然な箇所がある
  - 起点が `selected[0]` と `origin` に重複している
  - 起点にも到着時刻がある（`arrival_time == departure_time`）
  - 区間（`legs`）が地点を**名前**で指している。同名の地点があると対応が壊れる
  - `legs` と `selected` の対応（`legs[i]` は `selected[i]` → `selected[i+1]`）が約束事でしか守られていない。`reorder_places` は並べ替えのたびに `legs = []` で捨てて対応を守っている
  - `end_time` は `build_route` の戻り値にしかなく、`Guidebook` に残らない

### しおりのイメージ（壁打ちで確認したもの）

紙の旅のしおりの形を目標にする。v1.0.0 では「家で、出かける前に眺める」用途に絞る（当日の現地利用・Google カレンダー連携は将来）。

```
 10:00  広島駅 集合・出発
   ↓ 徒歩30分
 10:30  原爆ドーム（60分）
   ↓ 徒歩10分
 11:40  平和記念資料館（60分）
```

しおりは「集まる場所」「訪れる場所」「そのあいだの移動」の組み合わせでできている。

## 決定

### 1. しおりをチャットレスポンスに同梱する（要確認）

`/v1/chat/completions` のレスポンスに `plan` キーを足す。別エンドポイント（`GET /plan` など）は作らない。

理由：フロントが会話IDを持っていないため、別エンドポイントではどのセッションの `plan` かを指定できない。同梱なら、文章と `plan` が同じ応答に乗るので食い違わない。

### 2. 場所・移動・起点・訪問を、それぞれ独立したオブジェクトにする

性質の違うものを一つの箱に混ぜない。

| オブジェクト | 役割 | 何でできているか |
|---|---|---|
| 場所（place） | 最小の部品。どの旅でも同じ | `name`・`lat`・`lng` |
| 移動（travel） | 最小の部品。直前の地点からここまで | `duration_min`・`distance_m`・`mode` |
| 起点（origin） | 場所に「集まる・出発する」役割を与えたもの | 場所 ＋ `departure_time` |
| 訪問（visit） | 場所に「訪れる」役割を与えたもの | 場所 ＋ `arrival_time`・`stay_minutes`・`departure_time` ＋ 移動 |

- **場所と役割を分ける。** 起点と訪問先は「場所」ではなく「役割」。同じ広島駅が、起点にも訪問先（お土産売り場の散策）にもなれる
- **起点は訪問に含めない。** 起点は訪れる場所ではなく、集まって出発する場所。到着も移動も持たない
- **移動は訪問の直下に、場所と並べて置く。** 移動は場所ではなく「その訪問」に属する（同じ場所でも、どこから来るかで移動時間が変わる）。`from` は持たせない。直前の地点は並び順で決まるので、名前による参照が要らない

### 3. plan の形

```json
{
  "choices": [{ "message": { "content": "..." } }],
  "plan": {
    "origin": {
      "place": { "name": "広島駅", "lat": 34.3972, "lng": 132.4753 },
      "departure_time": "10:00"
    },
    "visits": [
      {
        "place": { "name": "原爆ドーム", "lat": 34.3955, "lng": 132.4536 },
        "arrival_time": "10:30",
        "stay_minutes": 60,
        "departure_time": "11:30",
        "travel": { "duration_min": 30, "distance_m": 2100, "mode": "walk" }
      }
    ]
  }
}
```

（座標・距離は説明用の概数）

| 論点 | 決定 | 理由 |
|---|---|---|
| 訪問のリスト名 | `visits` | 起点を外したので、全要素が「目的を持って訪れる場所」になった。stop（止まる地点）より意味が正確 |
| 場所の項目 | `name`・`lat`・`lng` のみ | v1.0.0 で場所の情報を使うのはリスト・ピン・表示範囲の調整だけ。使う側が決まっている項目だけを入れ、必要になったら足す |
| `place_id` | 入れない | v1.0.0 で使う場面がない。起点（`geocode_place` の結果）には無いため、入れると起点だけ `null` になる |
| `address`・`type`・`description`・`summary`・`opening_hours`・`reviews` | 入れない | 表示する画面が v1.0.0 に無い。施設の説明はチャットの文章で AI が行っている |
| 開始時刻 | 持たない | `origin.departure_time` そのもの。二重管理を避ける |
| 終了時刻 | 持たない | 最後の訪問の `departure_time`（到着＋滞在）。`build_route` の `end_time` と同じ値になる |
| 移動の `mode` | 持つ（v1.0.0 は常に `"walk"`） | 公共交通を足すとき、形を変えずに済む |
| 移動がないとき | 訪問には必ず `travel` がある。起点と同じ場所なら `duration_min: 0` | 「移動しなかった」と「移動の情報がない」を区別する |
| 滞在時間 | 60分固定のまま（`wrapped_tools.py:178` の `STAY_MINUTES`） | 形は訪問ごとに値を持てるので、将来の最適化（v2.0.0 以降）で値の決め方を変えても形は変わらない |

### 4. ルートが組めていないときは `"plan": null`

`plan` キーは常に存在させる。`Guidebook.is_ready()` が `False` なら `null` にする。フロントは「`plan` が `null` かどうか」だけで分岐できる。

### 実装の方針

- `Guidebook` の形は v1.0.0 では変えない。AI の作業メモとしての役割があり、変えると `build_route` とプロンプトに影響が広がる
- `Guidebook` から `plan` を作る**純粋関数**を一つ用意し、レスポンスを返す直前に呼ぶ。外部 API を呼ばないので、`tests/test_wrapped_tools.py` と同じ流れでテストできる
- 対応関係：`origin` ← `selected[0]`、`visits[i]` ← `selected[i+1]` と `legs[i]`、`mode` は定数 `"walk"`

## 未決定事項（次の会話で決める）

- **フロントでの保存先。** 候補は (a) 新しい slice を作り永続化しない（チャットIDをキー）、(b) `ChatInterface`（`types/chat.ts:12-19`）に `plan` を足す。(b) は永続化・エクスポート・migrate に影響し、`store.ts:79` の `version: 8` を上げる必要がある。v1.0.0 は「永続化は触らない」方針のため (a) が有力。`createPartializedState` が許可リスト方式かを先に確認する

## 結果

### 得たもの

- 地図（3-3・3-4）と名前リスト（2-2）が、文章の解析なしに作れる
- 起点と訪問先が同じ場所でも表せる
- 「到着がない」「移動がない」が、`null` の約束事ではなく形そのもので表せる。`visits` の要素には `null` の項目が一つもない
- 区間と地点の対応が並び順で決まり、名前による参照の問題が起きない
- 将来の拡張を、既存の形を壊さずに足せる
  - 最終目的地（ホテル・駅）：`origin` と対になる `goal`（場所 ＋ 到着時刻 ＋ 移動）を足す
  - 経路線（polyline、4-6 Should）：`travel` の中に足す
  - 公共交通：`travel.mode` の値を増やす

### 諦めたもの

- **`Guidebook` と `plan` の形が異なる。** 変換関数を一つ持ち、`Guidebook` 側の変更に追従させる必要がある
- **計画書の記述を書き換える。** 受け入れ条件3・2-2・3-3 は `plan.stops` で書かれていた（2026-10-11 に `plan.visits` と `plan.origin` へ更新）
- **地図で起点を別扱いにする。** 番号付きピンは `visits`（1, 2, 3…）、起点は別の印にする。起点と訪問先が同じ座標だとピンが重なる（3-3 で扱う）
- **起点と同じ場所への訪問は、形では表せるがロジックではまだ作られない。** `build_route` は起点と同名の候補（`wrapped_tools.py:359` の `visited = {origin}`）と 150m 以内の候補（`MIN_SPOT_DISTANCE_M`）を除外している
- **古い plan が返ることがある。** `build_route` がエラーを返したターンでは `Guidebook` が更新されず、前回の結果が残る。v1.0.0 では許容する

### 再検討のきっかけ

- フロントが会話IDを持つようになったとき（同梱か別エンドポイントかを再検討する）
- 地点の説明・口コミ・営業時間を表示する画面を作るとき（場所の項目を足す）
- 最終目的地を指定できるようにするとき（`goal` を足す）
- `Guidebook` の役割を「作業メモ」と「しおり」に分ける設計変更を行うとき
